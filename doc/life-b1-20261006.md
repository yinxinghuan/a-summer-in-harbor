## 动作接口与可信host

原Action envelope继续使用action_id/expected_version/scene/position/target。新action形式 `life:<verb>`、payload唯一字段 `{command: ...}`，额外proof/奖励/物件数量字段拒绝。ref必须完整固定版本。

| verb | command字段 | host必须证明 |
|---|---|---|
| buy-seed / sell | ref | 当前crop-counter邻近，营业；规则再检查钱/物 |
| plant | ref, plot | 当前已授权可耕地、相同几何/场景/目标、未占用 |
| water / harvest | plot | 当前真实地块邻近；规则按固定ref计算成熟 |
| save-seed | ref | 行囊动作合法；consume1产物→同版本seed1，无种子卖钱 |
| accept-order | ref | Theo已介绍、当前在场邻近、信息前提实际读过 |
| deliver-order | 无 | Theo在场邻近；规则核对pin的两份/钱/期限 |
| close-order | 无 | 行囊在途订单存在且已过期；不扣货 |
| observe-animal | animal, behavior | 一期真实个体、当前真实可见姿态和足点/保护区、邻近 |
| share-dani | 无 | Dani已介绍、当前在场邻近、分享前提已读 |
| display-gift | slot, gift可省略 | 已注册租屋展示槽位；省gift是撤展示 |
| news-memento | edition | 当前旅程已读来源与已提交虚构选择，固定edition/hash |

`createLifeRuntime(base, registry, {admit})` 是接口接缝；不提供会默认放行的host。host是服务端依赖，admit接收clone以免修改输入。返回的scene/target必须与实际Action一致，位置先走原walkable。真正的目标注册、邻近、几何、阅读完成与来源真实性由owner实现后再启用。QA host只用于规则/事务实验，没有复制到生产。

观察规则额外核对acceptedAnimals个体/visualVersion及当前slot的场景和sun-rest/sleep；不会增加熟悉度或改变一期animal memory。日程允许不能证明当下画面：例如招呼后的attention可能暂时覆盖sun-rest，B2必须有可信当前姿态条件；不能直接把客户端报告的pose塞进admission。新闻测试使用明确qa-frozen-edition/hash夹具，不冒充真实新新闻。纪念条目固定第一次来源；当前不是无限新闻图鉴，后续主题需独立设计。

## 旧档、版本与故障

1. `upgrade(s) = s`，无lifeV1的旧JSON读入、重启再读均不改写。原flags/history/奖励/动物字段与根菜畦不动。
2. 首个成功life动作克隆、固定旧seed/produce批次和plot refs，在原CAS提交里连同该动作一起写入。重复pin不会补奖或新建发现，失败候选不落盘。原旧动作在无lifeV1时不触发迁移。
3. lifeV1存在后，原作物动作继续调用旧applyCrop，只把已发生的delta镜像到legacy账本。原动物/故事动作与其他原字段照常保留。未写进root的虚构数量不能被消费。
4. items聚合数量，lots以固定版本和kind聚合；每次使用显式ref，不把v2货当v1订单。lot记录first/last来源，是汇总批次，不宣称逐件全谱系。旧库存安全非负整数继续沿用，新物品每key9999；最多64版本批次、64发现、128轻事件，原history仍500。
5. 旧v1播种、库存/已接受订单在v2出现后仍按旧ref结算；部署必须保留所有被引用定义。止新时关闭版本enablement，不删除定义/成熟植物/货品/订单/历史。缺ref明确拒绝，不静默换成最新crop。
6. 现金上限在扣货/发礼之前检查，订单995+10或单售998+4均原子拒绝。gift一份不能占两个slot；撤展示不删库存或发现。
7. 原authority一次事务提交head/journal/receipt；同action_id重放不重复收钱、交货、关系、首礼、时间或事件。payload改变拒绝，旧版本零写入，owner隔离、重启/receipt恢复已测。原客户端late-receipt/read-latest机制复用，B1未改客户端，新增UI故障实验属于B2。
8. 两个真实SQLite连接竞争实际只提交一次；原同步SQLite可能让败方收到BUSY。此次没有改变vendor、重试服务或证明PG多进程表现；生产PG需要专用QA配置和实际事务测试。
