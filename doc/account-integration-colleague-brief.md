# 《海湾新生活》账号接入协作说明

更新：2026-10-01。当前阶段：本地开发与联调准备，暂不部署上线。涉及新增凭据、权限或对外开放测试入口，先经项目负责人确认。

## 一、希望完成的体验

玩家在 AlterU 登录后进入《海湾新生活》。同一个账号换手机或浏览器，继续同一份服务端进度；换另一个账号或退出登录，不再读取、显示或继续写入前一个账号的存档。

游戏永久 UUID：`e78df027-7ef4-4d49-82eb-ea91f03d9fb3`。

## 二、我们已有的部分与当前缺口

- RPG 后台已有：权威剧情状态、玩家旅程目录、版本冲突处理、动作幂等与断线恢复，以及 PostgreSQL 接头。海湾本机预览用 SQLite；本作正式 PG 接入尚未完成实际验收。
- 平台已有：登录、宿主桥接 `callAigramAPI`，宿主为平台 API 请求附加登录认证。
- 当前公开 RPG 示例通过签名浏览器 Cookie 区分玩家；这尚未绑定 AlterU 的稳定账号。
- 旧托管服务已有 `createRpgProxy(resolveVerifiedActor)` 适配器，但示例中的 `yourExistingLoginVerifier(request)` 是占位，当前资料没有说明如何接入平台实际登录验证。

**本次需要补齐的一段：将平台已经验证的“当前登录玩家身份”，交给游戏自有 RPG 后台。** 同事只需提供现有接口合同或接入示例；无需提供完整登录系统源码、数据库或用户密码。

## 三、请先确认平台目前支持哪一种接法

优先复用已有方式，以下任选实际支持的一种，不要求同时建设：

1. **已有登录后台代理游戏请求。** 游戏通过宿主桥接或已认证入口发请求，平台先验证当前登录玩家，再由可信后台转发给 RPG 服务。请给出入口、调用示例，以及 RPG 服务如何确认转发身份确实来自平台。需明确浏览器伪造的同名身份头会在哪里被移除。
2. **已有短期登录证明或身份交换接口。** 游戏经宿主取得短期证明，游戏后台按平台既有方法验证，得到稳定玩家 ID。请给出取得/刷新方式、验证接口或签名验证文档。

如果此前已在某款游戏接通，请直接给出**游戏名称、接入文档/模块位置和脱敏调用示例**。我们优先沿用它，不要求重新设计。

## 四、所需接口信息

| 项目 | 请说明的具体内容 |
| --- | --- |
| 入口与调用方式 | SDK/桥接方法或 API 地址、HTTP 方法、请求/响应示例；由游戏浏览器、宿主还是游戏后台调用 |
| 身份验证 | 平台在哪一步验证登录；游戏后台如何验证证明或可信代理来源；如果需要服务端配置，请只列配置名与安全配置方式 |
| 稳定玩家 ID | 验证结果中哪个字段是权威账号 ID；同账号在 iPhone、Web、Telegram 等入口是否一致；若不同，平台是否提供归一后的账号 ID |
| 玩家与作者区别 | 返回的是当前游玩者，而不是游戏创建者、发布者或被查看资料的用户；请确认该语义 |
| 游戏范围 | 游戏 UUID 怎样传递与绑定；Remix 新 UUID 怎样隔离；是否已有相应 scope/audience/路由限制 |
| 生命周期 | 登录有效期、刷新方法、退出/切换账号的通知或检测方式；过期、撤销和未登录的响应；后台最迟多久能获知失效 |
| 运行环境 | iPhone AlterU 内、Web iframe、Telegram/Android 中支持情况；本地开发怎样调用，已有测试入口或 origin 限制是什么 |
| 已有文档/示例 | 可给现有 SDK 的用法或脱敏代码；内部登录源码无需交付 |

采用签名证明时，再提供所用算法、issuer/audience、有效期规则、公钥/JWKS 与轮换方式；采用后端验证接口时，提供请求/响应、失败码和限流约定即可。遵循平台实际合同，不预设 JWT 或某一种 token 格式。

`window.Aigram.telegramId` 可以用于界面识别当前用户；游戏后台收到浏览器转发的同一个字符串时，仍需要可验证的认证来源。请提供的是这一段接线，而不是再次确认这个字段的名称。

## 五、需要协助的联调条件

1. 提供可使用现有登录流程的测试环境；说明本地游戏如何进入这条真实认证链路。若只能通过一个临时测试路由联调，先说明所需变更与权限，我们确认后再安排，不直接改生产。
2. 提供两个测试账号 A/B 的使用安排。可以由同事自行登录配合，无需把密码或长期 token 发给我们。
3. 账号 A 在两个独立浏览器环境/设备分别登录，用于验证真正的跨设备恢复；同事说明哪些客户端可配合。
4. 如认证失败，协助按脱敏 request ID 查平台认证结果与错误码；不在日志/聊天中回传完整 Cookie、token 或用户存档。

先完成接口核对，再安排联调。新增服务凭据由维护者通过安全渠道配置到后台；任何新增凭据、安全权限、对外入口都先向项目负责人确认。

## 六、我们负责的接入和验收

我们负责把验证后的账号 ID 接到现有 RPG 玩家目录，完成前端登录变化处理、缓存/草稿/待提交动作隔离，以及以下测试：

- **同账号跨设备：** A 在设备一取得钥匙等进度；设备二登录 A，读取同一旅程和最新状态；再推进一次，设备一重新读取可见新进度。
- **不同账号隔离：** B 看不到 A 的目录、历史、草稿；在允许的测试环境中，直接请求 A 的旅程 ID 也被后台拒绝。
- **切换与登出：** A 切 B 或退出后，界面清除 A 的可见资料；A 的旧待提交请求不会以 B 身份继续发送。认证失效时停止写入，不偷偷新建匿名身份绕过。
- **认证负例：** 按实际合同检查伪造/过期证明或身份头；只有验证成功的身份能操作对应存档。
- **恢复与冲突：** 断线后以原动作 ID 确认结果，不重复奖励；旧设备的过期版本不能覆盖新设备进度。

现有本地试玩进度先保留在原身份下，不自动合并进账号。若以后需要访客存档转账号，再明确迁移规则并验证两边归属。

通过真实认证链路后，我们再把可复用接法、失败处理和测试方法写回 RPG 制作技能。模拟账号、QA 专用登录或复制浏览器 Cookie 不作为真实 AlterU 跨设备验收。

## 附：为何没有直接复用旧云存档凭证方案

旧 `rpg-story-session-production` 曾描述将随机访问凭证放入平台存档，再在新设备恢复。该技能自己也标注它是凭证持有者隔离，不是账号认证。现有 `get/data/list` 原始文档说明它会返回最近六个用户的存档，因此我们不把可访问私密 RPG 进度的凭证放入该列表。

另一个旧服务的可信平台代理边界可作为参考，但它使用不同的 v1 服务接口；海湾当前使用 PG 权威接头，我们会复用身份验证边界并适配现有接口，不把两套服务的路径与凭据混用。
